# 博客写作风格

把文章写成一个实际做过事情的人在向同行分享：**遇到了什么问题，为什么这样查或这样做，结果说明了什么，还有哪些事情不能确定。** 不要写成产品宣传、百科词条或只有正确答案的操作手册。

本 skill 提炼自当前博客的已发布文章，默认面向技术写作。这里的规则是风格偏好，不是必须逐项出现的文章组件；用户明确的体裁、长度和格式要求优先。

## 使用流程

1. **确定任务与素材。** 区分写新文章、改写、提纲和审校。整理已有的场景、问题、环境、操作、证据、结论和限制，不要求用户机械地填满表格。
2. **校准语感。** 阅读 [原文依据与对照示例](references/style-evidence.md)，重点看与当前体裁相近的部分。该路径相对于本 skill 目录；其中的博客源文件路径相对于博客仓库根目录。脱离仓库使用时，直接使用已收录的摘录即可。
3. **划清事实边界。** 区分已观察到的事实、解释这些事实的推测、尚缺的验证。影响结论的关键信息缺失时，先问少量必要问题；否则用中性表述继续，或在草稿中明确标记 `【待补充：具体内容】`。
4. **按题目选择结构。** 从下面的体裁中选一个主线，删除无必要的章节。不要给短工具记录强加完整复盘框架。
5. **写完后自检。** 写作或改写任务默认只交付标题和正文，不附“我如何模仿了你的风格”。提纲任务只交付提纲；审校任务指出具体位置、问题和改法。

## 叙述立场

- **以实践者而非全知讲师的口吻交流。** 默认读者有开发或运维基础，能看懂命令，但未必理解当前机制；解释关键原理，不从所有基础知识讲起。
- **“我”讲个人经历，“我们”讲团队实践或带读者一起分析，“你”用于操作提示。** 只有素材明确支持时，才能写“我们生产环境”“最近我解决了”。没有亲历素材就从问题或假设场景切入。
- **过程本身有价值。** 保留真正影响排查方向的失败尝试、排除项和转机，不把复盘改成一路正确的事后诸葛亮；也不为制造故事刻意添加弯路。
- **结论有力度，但有边界。** 可以明确推荐某个方案，也可以承认“没有直接证据”“这里只是初步定位”。不要把相关性写成因果，把缓解写成彻底解决。
- **务实而不板正。** 可以少量使用“折腾”“大杀器”“这里就不卖关子了”等口语，但不要每节都插入俏皮话，也不以夸张语气替代分析。

## 标题、开头与收尾

### 标题直接对应读者的问题

优先采用具体技术对象加问题、动作或影响，例如：

- `一个 [具体现象] 问题排查过程`
- `[技术/配置] 对 [指标/行为] 的影响`
- `为什么 [某种机制或建议]`
- `如何 [完成具体任务]`
- `[工具] 使用总结`、`[工具] 分析 [具体问题]`
- `[问题] 的一种方案`

标题可以带“诡异”“折腾记”这类轻微个人色彩，但必须有实际内容支撑。避免“震惊”“保姆级”“一文彻底掌握”“终极解决方案”等营销式承诺。

### 开头尽快落到具体事情

- 排障文：交代遇到什么异常、影响了什么，以及为什么值得记录。通常一两个自然段足够，不先铺一大段行业背景。
- 原理或配置文：直接提出“是什么、为什么、应该如何设置”中的核心问题。需要时先给简短结论，再展开解释，不刻意吊胃口。
- 工具文：说明当前缺少什么能力、为什么现有方式不够用，再引出工具。
- 方案文：先列目标和约束，再讨论实现。不要一开头就宣称某方案普遍最好。

### 收尾回到问题，不拔高主题

总结实际确认了什么、在什么条件下推荐使用，或这次真正学到了什么。有复盘价值时可以坦诚写自己忽略的细节。结尾可以很短，也可以直接停在验证结果或可用配置上；不强制添加总结、展望、邀评或“后续分享”。

## 按体裁组织内容

| 体裁 | 推荐主线 | 重点 |
| --- | --- | --- |
| 排障复盘 | 现象与环境 → 排查与排除 → 新线索 → 原因分析 → 处理与验证 → 简短复盘 | 让读者知道每一步为什么发生；尚未证实的根因不能用章节名强行坐实。 |
| 原理解释 | 具体疑问 → 必要概念 → 一个完整实例或流程 → 机制解释 → 使用条件 | 借请求流向、进程行为、数据变化讲原理，不只堆定义。 |
| 部署或实践教程 | 目标与环境 → 必要原理 → 分步配置/实现 → 检查结果 → 注意事项 | 操作和原因交替出现；既说明怎么做，也说明如何确认做对了。 |
| 方案比较 | 需求与约束 → 各方案的原理和实现 → 优缺点与适用场景 → 条件化推荐 | 不只给优缺点标签，要说清版本、回滚、部署成本等实际影响。 |
| 工具短记 | 任务与障碍 → 需要的字段或能力 → 命令/脚本 → 结果解读 | 可以不分节，没有必要补长篇背景和总结。 |
| 生活随笔 | 简短感受 → 时间顺序中的几个阶段 → 行为、对话与变化 → 自然收束 | 按下面的生活分支处理，不套技术文章结构。 |

技术长文优先使用 `## 0x01 现象`、`## 0x02 排查过程` 这样的二级标题，子节使用 `### 2.1 系统资源`，编号保持对应。标题写具体对象或动作，不全用“背景、分析、方案”等空泛词。

这不是硬性格式：旧文也有中文数字或不编号的标题。改写已有文章时优先保持原有层级；短文可不编号，不为了凑齐 `0x01` 到 `0x05` 增加内容。

## 推进论述的方法

技术段落尽量形成这样的局部链条：**当前疑问 → 为什么看这个地方 → 如何观察或操作 → 结果 → 这个结果支持什么、下一步看哪里。** 不必把这几个词写成固定小标题。

- 用因果关系衔接步骤：“既然……那就……”“通过上面的分析……”“但是这里有个问题……”。不要只写“首先、其次、最后”而不解释步骤之间的关系。
- 用真正的问题承上启下：“那为什么只有部分请求出现这种情况呢？”问完紧接解释、验证或待验证的方法，不连续堆修辞性反问。
- 抽象机制尽量落到一个具体实例，沿同一条请求、同一份配置或同一组指标解释。不要每一段切换一套例子。
- 展示正常与异常、修改前与修改后、不同方案之间的对照，明确比较条件。数字来自素材；没有数据就不要补造提升比例和耗时。
- 解释收益时顺带交代代价、例外和不适用的条件。常见写法是“这个方法可以……，但是……，因此更适合……”。

## 措辞与节奏

- 使用简体中文，技术名词、命令和字段保留英文。陌生缩写首次出现时补全称或简短中文解释，之后直接使用缩写。
- 每段围绕一个判断或动作展开，通常几句话即可。复杂因果可以适当展开，不写成每句话单独成段的碎片，也不要为了简短省略推导。
- 保留“这里”“其实”“比较”“当然”“一般情况下”“需要注意的是”等自然口语，适量使用；它们用于引导理解和限定条件，不是必须复刻的口头禅。
- 用“也就是说”“简单来说”“举个例子”把术语落回具体行为。类比用于降低理解成本，不能替代技术依据。
- 圆括号可补充英文、简称、条件或轻微旁白；补充过长时另起一段，避免一句话套多层括号。
- 可以用“禁止、必须、推荐”区分实践规范的强度，但要给出理由和适用范围，不把个人经验升级成所有场景的硬规则。
- 不模仿原文中偶发的错别字、重复、未完成句子、错序编号、失效链接和错误代码语言标记。保持术语及中英文间距一致，比机械复制排版瑕疵更重要。

## 代码、图表与引用

- 命令、配置键、路径、指标使用行内代码；关键区别、风险和限制可以加粗，不要整段加粗。
- 代码块标明正确语言，如 `bash`、`python`、`yaml`、`nginx`、`dockerfile`。示例应足以理解和使用，避免只有省略号的伪完整代码。
- 代码前说明解决什么问题，代码后解释关键参数、字段、输出和判断方法。不是把脚本贴出来就算讲解完成。
- 区分实际运行结果、预期结果和演示数据。涉及生产变更时写明前提、验证方法及重要副作用；仅写文章不等于获准执行文章中的命令。
- 图是论据，不是装饰。已有图片可采用 `![图1、具体说明](实际图片路径)`，正文指出看哪一列、哪条曲线、哪两个包，以及能推出什么。
- 不编造截图、日志、抓包、链接或“如下图”的内容。缺图时改成能独立理解的文字；需要保留制图任务时用明确的待补充标记，不生成假图片地址。
- 字段解释和方案对比适合表格；流程、步骤和若干选择适合有序列表；连续推理仍用自然段。不要把整篇文章拆成清单。
- 参考资料优先实际使用过的官方文档、issue、工具仓库或相关技术文章。链接放在对应论述附近，较多时可在末尾列“参考文档”；不要生成看似真实但未核实的来源。

原文是表达方式的样本，不是所有技术结论都可直接复用的依据。写作时核对当前版本、命令语义和适用条件；改写时保留原材料的事实及不确定性，发现疑点应指出或请求确认，不悄悄改造成“已验证”的结论。

## 生活随笔分支

目前生活类仅有一篇样本，因此只采用其可观察的特点，不把它推广为作者全部生活写作的固定习惯。

- 以一个简短感受开场，用有变化的阶段命名章节，不使用技术文的 `0x` 编号。
- 顺着实际时间讲事情，保留日期、人物行为、日常细节和原话，用前后变化体现情绪，而不是频繁评价情绪。
- 语气亲近、朴素，可以有轻微幽默；少用华丽意象、大段抒情和强行升华。
- 结尾可借一句对话或一个小变化呼应开头。人物、对话、日期和心理判断必须有素材支持；不知道的内心活动不要代写成确定事实。

## 在当前博客中落地

仅在用户要求创建博客源文件时应用这些约定；普通成文请求不自动附加 Hugo 元数据。

- 技术文章位于 `content/posts/`，生活文章位于 `content/lifes/`。
- 写文件前参考同类文章及对应的 `archetypes/posts.md` 或 `archetypes/lifes.md`。标题放在 front matter 中，正文通常从导语、二级标题开始，不重复一个一级标题。
- `slug` 根据新文章生成，不照搬模板中的固定值；日期使用实际确定的日期，不复制样本的旧日期。
- 新稿默认 `draft: true`，除非用户明确要求发布。改写已有文件时保留其日期、slug、aliases、分类及发布状态，除非用户要求调整。
- 图片使用已有的文章资源目录或已提供的远程地址，不臆造存储路径。不要为了使用本 skill 修改网站配置或旧文章。

## 交付前自检

- 开头是否已经说明具体问题，而不是泛泛介绍技术的重要性？
- 核心步骤是否解释了为什么做，关键证据是否得到解读，而非只贴命令和截图？
- 是否保留了真正影响结论的排除过程、限制条件和方案取舍？
- 有没有把推测说成事实，或捏造个人经历、指标、对话、执行结果及来源？
- 结构和篇幅是否符合当前体裁，没有强行套编号、总结或复盘感想？
- 语气是否像同行分享，既直接又不假装全知，没有堆口头禅和营销表达？
- 代码语言、术语、单位、编号、图片引用是否一致；待补充项是否明确可见，没有藏进貌似完整的成稿？
