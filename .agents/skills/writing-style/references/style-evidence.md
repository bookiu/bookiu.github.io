# 原文依据与对照示例

本文用于校准 `writing-style` 的判断，不是新的文章模板。下方引用均为原文摘录；“写法提炼”是归纳，不是作者原话。最后的改写对照是专门构造的演示，不能当作作者经历。

## 样本边界

- 创建本 skill 时，`content/posts/` 中有 29 篇 `draft: false` 的技术文章，`content/lifes/` 中有 1 篇已发布生活文章。
- 重点精读了跨 2019—2024 年的排障复盘、原理解释、工具记录、k8s 实践和生活随笔；另对《Kubernetes折腾记：搭建集群》《系统安全加固技术方案》等长文抽查了开头、章节与结尾。
- 排除 `content/posts/example-post.md`（测试草稿）、主题文档、生成站点 `public/` 和页面元数据，不把它们当作作者文章的语料。
- 结构盘点中，29 篇技术文章有 23 篇出现 `0x` 二级标题，26 篇包含围栏代码块，29 篇包含 Markdown 图片。这说明分节、代码和图解是明显偏好，**不意味着新文章必须有图片、代码或固定章节数量**。
- 所有 `content/...` 路径均相对于博客仓库根目录。只复制 skill 目录到别处时，无须再访问源文件，以下摘录已足以提供语感参照。
- 这些摘录只作为表达和结构依据；其中技术内容仍需结合版本及实际环境核验。

## 1. 开头交代实际异常与记录动机

来源：`content/posts/solve-nginx-200ms-latency.md`

> 最近生产环境 Nginx 遇到了部分请求延迟增加200ms的情况，深入排查解决后觉得挺有意义的（包括排查过程），所以这里记录分享一下。

写法提炼：一句话完成“发生了什么—为什么写”。“包括排查过程”揭示了文章的重心不只是公布答案。不要把这一特点机械简化为每篇都必须以“最近生产环境”开头。

同篇的结构是“现象 → 200ms 的来源 → 深入排查 → 根因及解决方案 → 总结”，其中排查过程继续分为系统资源、日志和抓包。宏观章节跟着问题推进，而不是按工具名随意拼接。

## 改写对照：模仿组织方式，不复制事实

以下素材与句子均为**虚构演示**，不出自博客，也不代表一次真实排障。

### 已知素材

- 同一应用的部分机器出现接口延迟升高。
- 同期 CPU、内存和请求量没有明显异常。
- 高延迟机器的 TCP 重传率更高。
- 尚未抓包，不能确认丢包位置或最终根因。

### 不贴近的写法

> 在当今复杂的云原生环境下，网络性能优化至关重要。本文将全方位揭秘接口延迟的底层逻辑，彻底解决网络性能难题。经过深入分析，我们精准定位到网络丢包这一根因。

问题：开头空泛、承诺过大，而且把尚未验证的线索写成了已经定位的根因。

### 更贴近的写法

> 同一个应用，只有部分机器的接口延迟升高。先看同期的 CPU、内存和请求量，并没有发现明显异常，那就需要从其它方向继续排查。
>
> 对比重传率后可以看到，延迟较高的机器，重传率也更高。这给后续排查提供了一个方向，但仅凭这个指标，还不能确定包丢在了哪里。下一步需要结合抓包，对具体连接继续分析。

贴近之处：直接说问题；保留排除过程；用结果推动下一步；不编造百分比、命令输出或“最终解决”的结局。它不需要机械复用“最近”“记录分享一下”才能具有相似语感。

### 一句话的取舍示例

不贴近：

> 该方案兼具高性能、高可用和极致灵活性，是最佳选择。

更贴近（假设方案确有这些性质）：

> 这种方式实现比较简单，但每次配置变更都需要重新发布，因此更适合配置不常变化的应用。如果需要热更新，就要考虑其它方案。

这里应学习的是“做法—代价—适用范围”的表达结构，不是把同一结论复制到每个主题。
